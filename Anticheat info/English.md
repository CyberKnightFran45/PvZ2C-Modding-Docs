# Chinese PvZ 2 - Anti-Cheat System Analysis

The Chinese version of PvZ2 has an anti-hacking system that detects changes to game data by comparing MD5 signatures generated using a different salt for each user.

This means that two accounts with the same number of Gems can have different hashes, because a user-specific value is used as the salt *(possibly a UID or a random seed)* so that signatures are unique to each player.

**Validated Data Schema**

| Description | Node      | Type     | Signature      |
|------------|:---------:|:--------:|:----------:|
| Coins  | c |      int    |    csign        |
| Gems   | g/gg |    int      |      gs      |
| Star keys | wsk |   WorldSpecificKey[]     |      ks      |
| Power-ups  | pr |   PowerupRecord[]    |      prs      |

## Anti-Cheat v1.0

The system used the `pcpid` field as its basis (a player GUID loaded from the `SexyAppActivity.xml` file) and compared critical data in `pp.dat`. If anomalies were found, they were reverted, leaving the local file clean.

An on-screen dialog displays the following messages:

```
[DIA_FAKE_SAVE_WARNING]
To monitor file data anomalies,
the system has deleted the abnormal data.

[DIA_FAKE_SAVE_WARNING_301]
To monitor file data anomalies,
the system has deleted the abnormal data.
<Error code: 301>

[DIA_FAKE_SAVE_WARNING_302]
To monitor file data anomalies,
the system has deleted the abnormal data.
<Error code: 302>
```

The data is deleted when you click OK.

**Affected versions: 1.0.1 - 1.6.3**

### Debug Check Details

The version with the Debug menu (v1.6.3) contains an interesting function:

```Global > Debug Check```

It checks the integrity of the current profile against a profile whose hash has been recalculated, and generates a decoded copy of both.
It works as follows:

1. First, it checks that local JSON copies of the data exist. These are generated by clicking the Save button in the interface and consist of two files: `PlayerInfo_backup.json` and `PlayerInfo_tmp.json`.

2. It compares the profile versions with the current version (`v` node). **The version identifier is 19 for v1.6.3.**

3. It checks the list of unlocked plants, looking for invalid IDs and verifying that they match the signature. It then generates the `Plants_backup.json` file, containing a list of unlocked plants written as typenames. **The `pp.dat` file stores them as numeric IDs.**

4. It checks for discrepancies in the player data `(PlayerInfo)` by recalculating the signatures in `tmp` and comparing them with the `backup`. **It will trigger an alert if it detects changes.**

### About Profile Signatures

I used IDA to look for the functions responsible for calculating the hash nodes before writing them.

`Reference version: 1.6.3 (Debug)`

Here is what I found.

1. The data is concatenated in different formats depending on the field type before the MD5 digest is computed.

2. The first string used in the various concatenations is obtained from `sub_262EC0()`. This function loads the `pcpid` node (PlayerID) from `SexyAppActivity.xml`.

3. The `a1` object is an instance of the profile `(PlayerInfo)`.

4. The `rs` field corresponds to the player's seed `(RandomSeed)`.

5. The `snuuid` field corresponds to the server's MAC address (a string with the value `02:00:00:00:00:00`).

6. For most scalar values, the actual integer is calculated first (since some are protected by BitsRotation and serialized in obfuscated form in the JSON, while being loaded into memory as `PropGrid.Hide`, hiding the actual value).

The following describes how the hashes are generated:

#### Signature for World Keys

- Used in: `sub_A9B1C8, sub_A9B360, sub_A9B4B4`

- Signature node: `wkssign`

- Format: `off_24EBAE0[0] -> 0x2045798 = "brGwm%siuy%deert%d10%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	wks
%s (4)	snuuid
```

#### Signature for Coin Amount

- Used in: `sub_A9B65C, sub_A9B7F4, sub_A9B948`

- Signature node: `csign`

- Formato: `off_24EBABC[0] -> 0x20456A8 = "asIen%seos%deosd%d11%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	c
%s (4)	snuuid
```

#### Signature for Stone Amount

- Used in: `sub_A9BAF0, sub_A9BC88, sub_A9C698`

- Signature node: `ssign`

- Formato: `off_24EBAF0[0] -> 0x20457F8 = "bgXes%sezz%detwd%d11%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	sc
%s (4)	snuuid
```

#### Signature for Gem Amount

- Used in: `sub_A9C840, sub_A9C9E4, sub_A9CB44`

- Signature node: `gs`

- Formato: `off_24EBAC0[0] -> 0x20456C0 = "Odsn%sasde%dNNsd%d22%s%d"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	g
%s (4)	snuuid
%d (5)	gg
```

#### Signature for Red Envelope Amount

- Used in: `sub_A9CD0C, sub_A9CEA4, sub_A9CFF8`

- Signature node: `rpsign`

- Formato: `off_24EBAFC[0] -> 0x2045840 = "Yun%s;ej%dlLinzzet%dk1%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	rp
%s (4)	snuuid
```

#### Signature for Star Keys

- Used in: `sub_A9D1A0, sub_A9D420, sub_A9D66C`

- Signature node: `ks`

- Serialization: each element is serialized as `"%s_%d"` (world name and number of keys). The final result is a single string representing all elements.

- Formato: `off_24EBAC4[0] -> 0x20456E0 = "(&^^%sOsP%dlsdfs%s33%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%s (3)	cadena serializada del vector wsk
%s (4)	snuuid
```

#### Signature for Power-ups

- Used in: `sub_A9D868, sub_A9DAE8, sub_A9DD34`

- Signature node: `prs`

- Serialization: each element is serialized as `"%s_%d"` (power-up type and quantity). The final result is a single string representing all elements.

- Formato: `off_24EBAC8[0] -> 0x20456F8 = ")2ld%sPPsd%dDSsf%d44%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)	direccion al buffer con la cadena serializada del vector pr
```

**NOTE: The third concatenated value should be a string (%s) to retrieve the contents, rather than the buffer address, which is dynamic and changes depending on the game's execution state. This is most likely a development error.**

#### Signature for Plant Pieces

- Used in: `sub_A9DF30, sub_A9E1A8, sub_A9E3EC`

- Signature nodes: `pprs`

- Serialization: each element is serialized as a pair using `"%d_%d"` (the first integer is the plant ID and the second is the number of pieces). The final result is a single string representing all elements.

- Formato: `off_24EBACC[0] -> 0x2045710 = "Owe%s_(sd%dNNlsd%s55%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada del vector ppr
%s (4)	snuuid
```

#### Signature for Accessory Pieces

- Used in: `sub_A9E644, sub_A9E890`

- Nodos firma: `asps`

- Serialization: each element is serialized as `"%s_%d"` (accessory name and number of pieces). The final result is a single string representing all elements.

- Formato: `off_24EBAF4[0] -> 0x2045810 = "iou%s_(sd%dUiowl%s92%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada del vector asp
%s (4)	snuuid
```

#### Signatures for Equipped Accessories

- Used in: `sub_A9EAE8, sub_A9ED44`

- Signature node: `ais`

- Serialization: each element is serialized as a structured field using `"%d_%s"` (ID of the plant carrying it and name of the equipped accessory). The final result is a single string representing all elements.

- Formato: `off_24EBAF8[0] -> 0x2045828 = "woq%s_&zo%doWzqk%s37%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada del vector pasi
%s (4)	snuuid
```

#### Signature for Plant Leveling

- Used in: `sub_A9F024, sub_A9F29C, sub_A9F4E0`

- Signature node: `psls`

- Serialization: each element is serialized as a pair using `"%d_%d"` (the first integer is the plant ID and the second is its level). The final result is a single string representing all elements.

- Formato: `off_24EBAEC[0] -> 0x20457E0 = "dja%sDM&%dOc%s-@ow%so2"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada del vector psla
%s (4)	snuuid
```

#### Signature for std::vector<int> (GameFeatures and others)

- Used in: `sub_A9F6DC, sub_A9F93C, sub_AA161C, sub_AA1874, sub_AA1A98, sub_AA1C94, sub_AA1F38, sub_AA21A8`

- Signature node: `ups, ugfs, wes`

- Serialization: each element is serialized using `"%d_"`. The final result is a single string representing all elements.

- Formato: `off_24EBAD0[0] -> 0x2045728 = "23d%sceaa%dmjLsd%s66%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada de p, gf o wm
%s (4)	snuuid
```

**Note: for `wm`, the internal serialization is "%d_%d_%d" (for the W, E, and S nodes, respectively).**

#### Signature for Unlocked Costumes

- Used in: `sub_A9FFB4, sub_AA0304, sub_AA0620`

- Signature node: `uas`

- Serialization: each element is broken down into `"%d_%d"` (costume ID and state), followed by `"_%d"` for sub-elements (each byte of the costume type).

- Formato: `off_24EBAE4[0] -> 0x20457B0 = "oang%s[ea0J%d)Mn%s>z%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada de ulokpa
%s (4)	snuuid
```

#### Signature for Costume Pieces

- Used in: `sub_AA0BDC, sub_AA0F0C, sub_AA1208`

- Signature node: `aps`

- Serialization: multi-level sub-elements are handled using `"%d"` (costume ID), followed by `"_%d"` (an array containing a single integer: the number of pieces).

- Formato: `off_24EBAE8[0] -> 0x20457C8 = "pqan%sz/qeY%d{qn%s#!%s"`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada de lpapi
%s (4)	snuuid
```

#### Signature for Purchase Information

- Used in: `sub_AA23A4, sub_AA255C, sub_AA26E0`

- Signature node: `rps`

- Formato: `off_24EBADC[0] -> 0x2045770 = "Odsn%sasde%dNNsd%s3fswe%sfefef%s99%s"`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%s (3)	rpi.rcp
%s (4)	rpi.rcpi
%s (5)	rpi.pdi
%s (6)	snuuid
```

Starting with version `1.7.5`, the following signatures were added:

#### Signatures for New Shop Information

Different signatures are stored as a kind of backup for purchases of certain resources.

- Signature node: `lprmd5`

- Fields: 

`rcpi` - amount of Gold Beans (same signature as `lsign`, described below)

`rcp` - amount of Coins (same signature as `csign`)

`pdi` - amount of Gems (same signature as `gs`)

---

#### Signature for Gold Bean Amount

The amount of Gold Beans obtained by opening Chests in older versions.

The value is derived using a rotate operation (ROR) and compared against a recalculated value for the new number of leaves using the following formula: `ptss + (extra * lmz)`

Where:

- `lmz` is the bean multiplier, with a default value of `1.0`

- `extra` is the number of additional beans (it can be 1 or 10)

This applies only when opening chests. The formula can be simplified by using the direct value of `ptss`, which produces exactly the same result: `derived = ROR(ptss, ptss & 0x1F) ^ ptss`

- Signature node: `lsign`

- Formato: `aaXes%smzz%dbdwd%d12%s`

- Parameters:

```
%s (1)	pcpid
%d (2)	rs
%d (3)  derived
%s (4)	snuuid
```

---

#### Signature for Unlocked Worlds (Plants Adventures)

- Signature node: `paws`

- Serialization: each element is serialized using `"%d_"`. The final result is a single string representing all elements.

- Formato: `uio%sHuy%dpe%srew-%sl4`

- Parameters:

```
%s (1) pcpid
%d (2) rs
%s (3)	cadena serializada de pawf
%s (4)	snuuid
```

---

#### Residual Signatures

The following literals remain in the code, but no functions use them:

`Owe%s_(sd%dNe2sd%s88%s`

`Odd%s_(sd%dNvbNd%s77%s`

---

Starting with version `2.0.0`, the following changes were made:

1. The `lprmd5` node changed from an object to an empty string (removed due to redundancy).

2. A new field named `oipi` (integer) was added to the `PurchaseInfo` class. This does not affect the generation of `rps`.

3. With the change to Worlds, the `wmed` node was added. However, `wes` is still generated from `wm` (now empty).

---

Once concatenation is complete, the MD5 hash is generated in `sub_1C38284`. There is no HMAC key or anything of the sort, just a custom digest with values that vary by user.

### Conclusions

I searched for the same literals in the latest version (`4.0.1` at the time this document was written), and they are still present. This indicates that the system uses the same principles to validate user data and determine whether it is legitimate.

The next step will be to modify a `pp.dat` file and reproduce the hashes with a script to test whether the data persists after entering the game or whether the system deletes it in the same way.

**NOTE: Swapping local data in versions later than `2.4.83` has no effect because the files are handled server-side. However, if you download an older version (such as `2.2.5`) and then update the game to the newest version, its system will migrate the data to the cloud, making the changes persist (this works as long as the anti-cheat does not detect anomalies).**
